## Context

modscape:spec SDD ワークフローは `requirements → design → implement → archive` の直線的なフローとして設計されている。しかし現実の実装では、SQL を実際にデータ基盤で実行するまで気づけない問題（データ型の不一致、カラム名の誤り、JOIN 前提の崩れ、想定外の NULL など）が頻繁に発生する。

現状、これらの発見を spec.md / design.md / tasks.md に反映する手段は暗黙的な手動編集のみであり、どのファイルを直すべきか、どう記録すべきかのガイドがない。

## Goals / Non-Goals

**Goals:**
- 発見した問題をユーザーが自由記述で渡すと、AI が適切な成果物を差分更新する
- 完了済みタスク（`- [x]`）は保持し、修正タスクを追加する
- フローの任意のタイミングで何度でも呼び出せる
- 更新した箇所をサマリー表示して何が変わったかを明示する

**Non-Goals:**
- `spec-model.yaml` の自動修正（YAML 操作は実装者が `modscape` CLI で行う）
- archive 済みの changes を遡って修正すること

## Decisions

### スキルの入力形式：自由記述テキスト

**決定**: ユーザーはエラーメッセージ・気づき・設計変更を自由記述で渡す。構造化フォームは使わない。

**理由**: 実際の発見は「エラーログをコピペしたい」「ふと気づいた」など形式が多様。構造化させると摩擦が大きい。AI が文章から更新箇所を判断するほうが自然なUXになる。

### 更新対象の判断：AI が推定する

**決定**: どのファイル（spec.md / design.md / tasks.md / questions.md）を更新するかは AI が入力内容から推定する。

対応方針：
- エラー・型不一致 → `spec.md` の AC 修正 + `tasks.md` に修正タスク追加
- 設計前提の崩れ → `design.md` の該当セクション修正 + `tasks.md` に修正タスク追加
- 未解決の疑問 → `questions.md` に Q-NNN で追記
- 複数に影響する場合 → すべて更新

**代替案**: 更新対象をユーザーが明示的に指定する → 却下。amend の呼び出し時点でユーザーはどのファイルを直すべきか必ずしも把握していないため。

### 完了済みタスクの保護

**決定**: `tasks.md` の `- [x]` タスクは一切変更しない。修正タスクは未完了の末尾または新しい `## Amend: <日付>` セクションとして追加する。

**理由**: 完了済み作業の記録は実装履歴として重要。上書きすると進捗が失われる。

### スキルのプラットフォーム構成

Claude Code（`src/templates/claude/spec/amend.md`）を正本とし、Gemini・Codex 版を派生として作成する。既存スキルと同じ構成。

## Risks / Trade-offs

- **AI の更新判断がずれるリスク** → サマリー表示で「何を変更したか」を明示し、ユーザーが確認・手修正できるようにする
- **質問の重複登録** → questions.md に追記する際、既存の Q-NNN と重複しないよう質問テキストで重複チェックを行う
