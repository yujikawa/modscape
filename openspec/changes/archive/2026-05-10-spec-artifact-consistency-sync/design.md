## Context

`modscape:spec` ワークフローは `spec.md`（要件）/ `design.md`（設計）/ `spec-model.yaml`（モデル定義）の3ファイルを中心に進む。現状の各スキルはそれぞれ一部のファイルしか更新しないため、設計・実装フェーズで発見が生じると残り2ファイルが置き去りになる。

特に問題になるケース:
- `amend` は `spec-model.yaml` を更新しない → モデルの修正が漏れる
- `design` 再実行は `spec.md` の AC を確認しない → 要件との乖離が残る
- 実装中のユーザー発言（「これが違った」）はコマンドにならないまま流れる → 3ファイル全部が放置される

## Goals / Non-Goals

**Goals:**
- どのスキル（`amend` / `design` / `implement`）でも、変更後に他2ファイルへの影響を自動確認する
- `amend` が `spec-model.yaml` の mutation を担当できるようにする
- `implement` 中の会話的な発見を、コマンド切り替えなしに3ファイルへ反映できるようにする

**Non-Goals:**
- 新スキルの追加（既存スキルの拡張のみ）
- `tasks.md` の自動再生成（ユーザーが明示的に `/modscape:spec:tasks` を実行する運用は変えない）
- Gemini / Codex バージョンの即時同期（Claude Code を先行させ後追いで可）

## Decisions

### 1. `design.md` を「派生物」と位置づける

`spec.md`（What）と `spec-model.yaml`（Exact）を正とし、`design.md` はその橋渡し文書とする。これにより「どれが基準か」の問いを避け、「何かが変わったら design.md も追従する」という一方向のルールを維持する。

### 2. 波及確認は「報告 + 自動修正」の2段階

変更後の波及チェックは:
- **軽微な修正**（列の型・制約・AC の文言修正）→ その場で自動修正してレポート
- **設計変更を伴う修正**（grain 変更・テーブル再設計）→ ユーザーに確認を求め、`design` 再実行を案内

判断基準: `spec-model.yaml` の構造（テーブル追加・削除・lineage 変更）が変わる場合は「設計変更」、列・制約・説明の修正は「軽微」とする。

### 3. `implement` の発見処理はインラインで完結させる

`implement` スキルが実行中に「発見的な指摘」を受けたとき、`amend` と同等のロジックをインラインで実行する。ユーザーがコマンドを打つ必要はない。発見の重さで分岐:

```
発見を受け取る
  ├─ 軽微（列・制約・AC）→ 3ファイル即修正 → 実装継続
  └─ 設計変更          → ユーザーに確認 → design 再実行を案内 → 実装中断
```

### 4. 各スキルに「波及確認レポート」ステップを末尾追加

新ステップを各スキルの最後に追加する。フォーマット:

```
## 波及確認レポート

| ファイル | 状態 | 内容 |
|---|---|---|
| spec.md | ✅ 影響なし | |
| design.md | ✅ 更新済み | Findings に追記 |
| spec-model.yaml | ⚠️ 要確認 | fct_orders.amount_jpy → amount に修正が必要 |
```

## Risks / Trade-offs

- **[Risk] 「軽微」と「設計変更」の判断ミス** → Claude が誤分類すると余分な中断が発生したり、必要な中断が省略される。軽微判断の条件（構造変化がないこと）を実装ドキュメントに明示して対処する。
- **[Risk] `amend` が `spec-model.yaml` を修正する際の CLI mutation 失敗** → validate コマンドで即座に検出し、エラーをレポートに含める。
- **[Trade-off] `tasks.md` は自動更新しない** → 3ファイル整合に集中し、tasks.md はユーザーが明示的に再生成する運用を維持する。ユーザー操作を1ステップ増やすが、tasks.md の過剰な自動変更を防げる。
