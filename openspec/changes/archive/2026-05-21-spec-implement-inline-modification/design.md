## Context

`/modscape:spec:implement` は実装中にユーザーから修正指摘を受けた場合、現行では「軽微な修正」と「設計変更」の 2 パスに分岐する。

- **軽微な修正**: `design.md` + `spec-model.yaml` を更新 → 続行確認
- **設計変更**: `design.md` の Findings に記録するだけで停止 → `/modscape:spec:design` への案内

問題は「設計変更」パスで、AI が design.md と spec-model.yaml を更新できる能力を持ちながら、Findings に記録して停止するだけになっている点にある。ユーザーが明示的に「修正して」と依頼した場合は、AI が 3 ファイル（design.md / spec-model.yaml / tasks.md）を一括更新してそのまま実装を続けられる方が自然である。

## Goals / Non-Goals

**Goals:**
- 修正の種類（軽微 or 設計変更）によらず、ユーザーが依頼したら AI がインラインで全ファイルを更新して続行できるようにする
- 更新完了後は「実装を続けますか？（はい/いいえ）」の一言確認のみ
- Claude / Gemini / Codex の 3 テンプレートと `openspec/specs/sdd-implement/spec.md` を同期更新する

**Non-Goals:**
- AI が自律的に発見した構造問題の扱い（現行の Findings 記録フローは維持）
- tasks.md の全再生成（`/modscape:spec:tasks` の呼び出しは不要。影響タスクのみ外科的に更新する）

## Decisions

### 決定 1: 「設計変更」パスを廃止し「インライン修正」パスに統一

**採用**: ユーザーが明示的に修正を依頼した場合は分類を問わずインライン完結とする。

**理由**: 軽微か設計変更かの区別はあくまでファイルの更新範囲の違いであり、いずれも AI が自律的に処理できる。ユーザーにコマンド切り替えを求める理由がない。

**却下した選択肢**: 「設計変更の場合は確認ダイアログを表示してから更新する」— 確認より操作の簡素化を優先する。

---

### 決定 2: tasks.md は全再生成ではなく影響タスクのみ外科的に更新

**採用**: 変更されたテーブルに対応するタスクのチェックを `[ ]` に戻す（または新規タスクを追加する）だけにする。

**理由**: `/modscape:spec:tasks` を再実行すると完了済みタスクのマージ確認が入り、かえって煩雑になる。影響範囲が明確な場合は外科的更新で十分。

**テーブル追加の場合**: 追加テーブルのフェーズ（Staging / Core / Mart）を lineage から判定して適切な位置にタスクを挿入する。

**テーブル削除の場合**: 対象テーブルのタスク行を削除する（完了済みであれば削除不要）。

---

### 決定 3: 続行確認の文言を統一

**採用**: 更新完了後は常に以下の形式で確認する。

```
✅ 修正完了。

| ファイル | 更新内容 |
|---|---|
| design.md | <更新箇所> |
| spec-model.yaml | <更新内容> |
| tasks.md | <変更したタスク一覧> |

実装を続けますか？（はい / いいえ）
```

**理由**: どの種類の修正でも出力形式を統一することで、ユーザーが迷わない。

## Risks / Trade-offs

- **[リスク] AI が tasks.md のフェーズ挿入を誤る** → tasks.md の更新後に内容を表示して確認を促す。
- **[リスク] lineage 変更で依存タスクの抜け漏れが生じる** → 変更テーブルの直接依存だけでなく、downstream テーブルも `[ ]` に戻す対象として提示する。
- **[トレードオフ] 設計変更でも停止しないため、ユーザーが気づかないまま不整合な状態になる可能性がある** → 更新内容の差分を明示的に表示することで可視化して対処する。
