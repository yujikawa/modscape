## Context

現在 `specs/<table-id>/spec.md` を **作る** 手段として `/modscape:spec:generate` が存在するが、作成後に **更新する** 手段がない。`/modscape:spec:amend` は SDD 実装ワークフロー内の `changes/<name>/` を対象にしており、ワークフロー外のテーブル仕様更新には使えない。

データチームは実装とは無関係なタイミングでもテーブルに関する知識を得る（対面会話、Slack、ドキュメント精読など）。その知識を即座に spec へ書き留める軽量コマンドが必要。

## Goals / Non-Goals

**Goals:**
- `specs/<table-id>/spec.md` に対してフリーテキストから知識を追記できる
- テーブルID指定の有無を問わず動作する（指定あり: 直接更新、指定なし: AI推定）
- 書き込み前に更新内容を確認するステップを挟む
- SDD ワークフローの外側に位置するスタンドアロンコマンドとして機能する

**Non-Goals:**
- `changes/<name>/` 以下のアーティファクト更新（それは `amend` の役割）
- spec ファイルの新規作成（それは `generate` または `requirements` の役割）
- 対話式の要件収集（それは `requirements` の役割）

## Decisions

### 1. コマンド名: `note`

**採用理由:** 「メモする」という行為を直接表す動詞。`update`（操作的すぎる）・`enrich`（やや堅い英語）より、実際のユースケース（忘れないうちに書き留める）に最も近い。

**代替案:**
- `update` — 汎用すぎて、何を対象にした操作か曖昧
- `enrich` — 情報追加の意味は正確だが日常語として重い

### 2. テーブル指定の扱い: オプション引数

```
/modscape:spec:note [table-id]
```

- 指定あり → 該当 `specs/<table-id>/spec.md` を直接対象にする
- 指定なし → フリーテキストを解析し、言及されているテーブル（または推定できるテーブル）を自動特定する

**理由:** 単一テーブルについて話すことも、複数テーブルにまたがる会話内容を貼ることもあるため、両方対応する方がユーザー体験が良い。

### 3. 確認ステップを必須にする

AI がセクションを判断して書き込む構造上、意図しない場所への書き込みを防ぐために確認ステップは常に実行する。

```
以下の更新を行います:

- specs/fct_orders/spec.md
  Known Issues: "Q1 2023 の updated_at は信頼不可"
- specs/dim_customers/spec.md
  Business Rules: "SCD Type2。grain は有効期間ごとの行"

続けますか？ [Y/n]
```

### 4. 書き込み先セクションの判断ロジック

フリーテキストの内容を以下のルールでセクションにマッピングする:

| 入力の性質 | 書き込み先 |
|---|---|
| ビジネスルール・計算ロジック・定義 | `## Business Rules` |
| 既知の問題・データ品質の注意点 | `## Known Issues / Caveats` |
| 背景・経緯・意図 | `## Business Context` |
| オーナー・SLA・更新頻度 | `## Overview` |
| 上記に分類できないメモ | `## Known Issues / Caveats` に追記（最も汎用的なセクション） |

### 5. 既存コマンドとの住み分け

`specs/<table-id>/spec.md` を操作するコマンドは複数あるが、役割が異なる:

| | `generate` | `note` | `amend` |
|---|---|---|---|
| 入力 | コード・YAML ファイル | フリーテキスト（会話・メモ） | 実装中の問題・エラー |
| 操作 | **新規作成** | **既存specへの追記** | 変更アーティファクトの修正 |
| 対象 | `specs/<table-id>/spec.md` | `specs/<table-id>/spec.md` | `changes/<name>/` 以下 |
| タイミング | SDD 開始前の bootstrap | いつでも（ワークフロー外） | 実装ワークフロー内 |

`note` が `generate` で代替できない理由: `generate` はコードを読んでspecを**作る**コマンドであり、人間の会話から得た知識を**追記する**用途には設計されていない。また `generate` は既存specを上書きしない（skip）ため、更新手段にもなれない。

### 6. specが存在しない場合の挙動

`specs/<table-id>/spec.md` が存在しない場合は書き込まず、警告を出して終了する。

```
⚠ specs/fct_orders/spec.md が見つかりません。
先に /modscape:spec:generate を実行してspecを作成してください。
```

**理由:** `note` の責務は「既存 spec への追記」であり、新規作成は `generate` の役割。責務を分離してコマンドをシンプルに保つ。

## Risks / Trade-offs

| リスク | 対策 |
|---|---|
| AI がセクション判断を誤り、意図しない場所に書く | 確認ステップで必ずプレビューを表示してからのみ書き込む |
| テーブル推定が外れて無関係なspecが更新される | 確認ステップで対象テーブルを明示し、ユーザーが修正できる |
| specが存在しない場合に暗黙的に新規作成される | 存在しない場合はエラーとして明示的に停止する |
| 複数テーブルにまたがる入力でパースが複雑になる | Gemini/Codex 版は Claude 版より実装が遅れることを許容する |
